# 与 dsh-genui 的关系评估

> 评估对象：[omdsh-dev/dsh-genui](https://github.com/omdsh-dev/dsh-genui)（npm `@changfenhuang/dsh-genui` v0.16.0，MIT）
> 评估时间：2026-11-08
> 结论摘要：**不建议把 dsh-genui 合并进本插件。**两者是同一目标下的两种输出形态，应当并存并明确分工；值得借鉴的是它的事件回环与常驻面板，而不是它的渲染实现。

## 1. 对方是什么

`dsh-genui` 是一个成熟的 DSH 官方生态插件，把**模型回复正文里的 JSON 围栏**实时渲染成可交互的原生界面：

```dsh-ui
{"items":[{"type":"stat","label":"本月营收","value":"¥128,430","delta":"+12.4%"}]}
```

机制（来自其源码与 README）：

- Host 半：注册 system prompt section（`STRUCTURED_OUTPUT` 段）、`render_ui` / `validate_dsh_ui` 工具、`fenceFeedback` 同回合纠错、bundled `genui` skill、静态资源路由（Mermaid / Three.js / ECharts 按需加载）。
- Client 半：通过 fence 注册扩展点接管 `dsh-ui` 围栏，在对话 DOM 内挂载 React 组件树。
- 能力：30+ 组件（布局/表格/图表/plot/表单/测验/音视频/Mermaid/3D/地图）、本地优先交互（排序、过滤、判卷、滑块重绘）、action 回环（按钮/表单把结构化事件发回模型）、常驻 Dock 面板、导出独立 HTML / `.genui.json`、会话级状态持久化。
- 依赖：React 18、ECharts、Mermaid、Three.js、MapLibre、KaTeX 等，重型引擎按需加载；Node ≥ 22.19 / ≥ 24（alpha 宿主）。
- 安装：`dsh plugin --profile web add @changfenhuang/dsh-genui`。

## 2. 本插件是什么

`dsh-answer-me-with-html` v0.1.0：模型写一份扩展 Markdown 草稿，Host 工具调用内置的 `am.mjs` **服务端渲染**成一页离线 HTML，页面落在会话工作区 `.dsh/answer-pages/`，用户在右侧 Document Preview 打开；工具卡显示标题、警告与错误。

- 输出：单个自包含 HTML 文件（可移植、可归档、可打印）。
- 交互：页面内主题/明暗切换、面板评论、`ask`、Reply（复制到剪贴板）。
- 依赖：仅 Node（桌面端用 Electron 自带 Node），渲染器 1 MB 左右。
- 安装：`github:ShanHaiFish/dsh-answer-me-with-html`，或本地目录。

## 3. 对比矩阵

| 维度 | 本插件 | dsh-genui |
|---|---|---|
| 输出形态 | 一页 HTML 文件 | 回复正文中的内联 React 组件 |
| 出现位置 | 右侧 Document Preview / 文件链接 | 对话正文 / 常驻 Dock 面板 |
| 模型输入 | 扩展 Markdown 草稿（约 600 token/页） | JSON spec 围栏（约 200–800 token/块） |
| 渲染 | Host 进程调用 `am.mjs`，自动布局/主题/STE 检查 | 浏览器端组件库 + 按需引擎 |
| 交互 | 页面本地；Reply/ask 靠剪贴板 | 本地优先 + action 结构化回传模型 |
| 流式 | 工具返回后一次成型（约 100 ms 渲染） | 边生成边渲染 |
| 持久化 | 文件持久；页面可离线分享 | 会话 + 内容指纹状态；可导出 HTML/JSON |
| 离线 | 单文件离线可开 | 导出文件内嵌运行时后离线可开 |
| 依赖体积 | ~1 MB，无前端框架依赖 | React + 多个重型引擎，按需加载 |
| DSH 接入面 | Host 工具 + skill + 工具卡 | prompt section + 2 个工具 + skill + fence 渲染器 + 面板 + 资源路由 |
| 适合内容 | 长篇解释、图多、需要打印/PDF/归档 | 仪表盘、表格、表单、测验、图表、音视频、交互决策 |
| 维护成本 | 小，固定上游版本 | 大，快速迭代（v0.16.0，测试/E2E/多宿主矩阵） |

## 4. 重叠与差异

**重叠：**

- 都试图让回答“更好读、更可操作”，都会引导模型产出结构化内容。
- 都在 DSH 里新增 skill 和工具；都会在会话里出现卡片式入口。
- 都能产出可离线打开的 HTML（我们原生，它通过导出）。

**差异（关键）：**

- **产物归属不同**：我们产出“文件/页面”，它产出“回复的一部分”。前者适合归档与分享，后者适合就地操作。
- **交互模型不同**：它的按钮能把动作发回模型形成闭环；我们的页面按钮只能复制文本，用户需要再粘贴回对话。
- **渲染成本不同**：我们是服务端一次成型、体积极小；它是浏览器端组件树 + 重型引擎。
- **内容语法不同**：扩展 Markdown vs JSON schema；互相转换会丢失结构（自动布局、STE、组件语义都不同）。

**冲突风险：**

- 两个 skill 的描述都覆盖“解释/对比/图表”等场景，模型可能对同一问题**同时**产出页面和 `dsh-ui` 围栏，造成重复表达与 token 浪费。
- 同时安装会增加首屏/会话的工具与提示词体积；客户端同时加载两套渲染器。
- 兼容矩阵不同：本插件验证 0.2.1-rc.2 / 0.2.2-rc.1；dsh-genui 声明覆盖 0.2.0–0.2.2-alpha 并单独验证 rc.3/rc.5，二者不是同一条验证线。
- 静态检查未发现直接技术冲突：工具名、skill 名、槽位、渲染入口都不同；但**运行时共存尚未实测**（见第 7 节）。

## 5. 集成选项与代价

| 方案 | 内容 | 工作量 | 风险 | 收益 | 建议 |
|---|---|---|---|---|---|
| A. 不集成，文档分工 | 明确“何时用哪个”，可同时安装 | 0.5 天 | 低 | 高：避免重复输出，保留各自优势 | **推荐** |
| B. 合并成一个插件 | 统一工具/技能/渲染器，页面与内联二选一 | 数周 | 高：schema 不兼容、依赖膨胀、维护翻倍 | 体验统一，但失去轻量 | 不做 |
| C. 让页面嵌入 GenUI 组件 | 在 `am.mjs` 页面里跑 GenUI 运行时 | 1–2 周 | 高：React/引擎注入、CSP、离线失败 | 页面更交互 | 不做 |
| D. 把 GenUI spec 转成页面 | 写转换器，输出我们的 HTML | 1 周+ | 高：结构丢失、双份维护 | 有限 | 不做 |
| E. 借鉴其能力自建 | 设置页、页面库/Dock、动作回环、内联缩略卡 | 3–8 天/项 | 中 | 补齐我们真实缺口 | 按需排期 |

## 6. 推荐

### 6.1 现在：不合并代码，明确分工

- **本插件**负责：长篇解释、图多的说明页、需要打印/PDF/离线单文件、希望在右侧预览里阅读和归档的内容。
- **dsh-genui** 负责：短小可交互的仪表盘、表格筛选、表单/测验、函数图、音视频、3D、需要按钮把动作发回模型的内容。
- **同一回答只用一种**；不要在一条回复里既调 `answer_me_with_html` 又输出 `dsh-ui` 围栏。
- 两个插件设计上可以同时安装（工具、skill、槽位、渲染入口均不重名），但正式使用前做一次共存验证。

### 6.2 建议的最小改动（P0）

1. README 增加“与 dsh-genui 的关系”一节（本次已加）。
2. 在 `skill/SKILL.md` 顶部增加一句决策规则（待批准）：*若 `genui` skill 可用，且内容更适合短小内联交互，则使用 GenUI；本工具用于长篇/图多/离线页面；不要两者同时使用。*
3. 不做运行时自动检测另一个插件，避免强耦合和版本判断。

### 6.3 值得自建的能力（不依赖 GenUI）

按优先级：

1. **设置页**：`plugins.bundle.config`，把 theme/mode/style/alwaysOn/outputDir 做成可编辑表单（我们目前只能改 profile patch）。
2. **页面库 / Dock**：列出当前会话生成过的页面，支持重新打开、删除、按时间排序（借鉴 GenUI 的常驻面板思路）。
3. **动作回环**：把页面里的 Reply / `ask` 变成结构化事件回传模型。需要自定义右侧预览 tab + postMessage 桥接 + 页面脚本改造，是最大的一项（5–8 天），等真实需求再排。
4. **内联摘要卡**：工具卡加页面缩略图/首屏预览（成本低，收益中）。
5. **导出 PDF/PNG**：上游 `am export` 已具备，可加一个工具参数或按钮（需 Chrome，作为可选功能）。

### 6.4 明确不做

- 不内置 GenUI 运行时或组件库（体积、许可、CSP、离线风险都不划算）。
- 不做 Markdown ↔ GenUI JSON 的双向转换。
- 不在本插件里复制 GenUI 的 fence 渲染逻辑（会和其客户端争抢同一围栏）。
- 不自动安装/启用 GenUI。

## 7. 共存验证计划（待执行）

如果决定同时安装，按以下顺序验证：

1. 在**临时 profile**（或 staging 环境）同时安装两个插件，确认：工具列表、skill 目录、system prompt 段、客户端 boot graph 均正常。
2. 桌面端与 Web 端各开新会话：
   - 同一问题分别验证“页面”和“`dsh-ui` 围栏”两条链路；
   - 确认没有一条回答同时触发两者；
   - 检查浏览器 Console 无两个插件互相干扰的报错；
   - 确认页面预览、fence 渲染、面板、工具卡均可用。
3. 卸载其中一个，确认另一个不受影响。
4. 记录版本矩阵（DSH 版本、Node 版本、两个插件版本），写入 README 的兼容性说明。

## 8. 结论

- **不需要把 dsh-genui 集成进本插件**：两者输出层不同，合并会同时失去“轻量、离线、可归档”和“内联、交互、动作回环”的长处。
- **需要的是分工与共存验证**：一条明确的“何时用哪个”规则，比代码合并收益更高、风险更低。
- **真正值得投入的是我们自己的缺口**：设置页、页面库、动作回环；这些可以独立演进，不需要绑定 GenUI 的版本节奏。
